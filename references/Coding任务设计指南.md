# Coding 任务设计指南

## 目标

设计一个能让模型在单轮提示词中实际产生不少于 400 次工具调用的 Coding 任务，同时不增加人工测试的工作量。

核心思路：把多个相互关联、需要真实跨模块改造的任务放进同一个首轮提示词，用“任务一、任务二、任务三……”拆清楚；靠仓库探索、功能实现、迁移、测试和回归自然达到内部轮次目标。文件底部只保留一个按需发送的备用提示词，靠脚本验收和统一验证清单控制人工测试成本。

合规边界：400 次是测评组织者设计任务时使用的内部目标，最终发给模型的提示词不得出现具体工具调用次数，也不得要求模型凑调用；应通过真实任务复杂度自然形成长程执行。

---

## 设计流程

1. 确认任务背景（已有项目、技术栈、已有功能）
2. 选择 2-4 个相互关联、能够形成真实跨模块工作的任务，明确先后依赖和共同回归范围
3. 设计一个完整首轮提示词，按“任务一、任务二、任务三……”拆分，内部评估其是否足以支撑单轮实际工具调用不少于 400 次
4. 首轮一次性写清任务背景、工具使用原则、各任务功能点、自动化验证和交付物，不依赖后续任务块完成核心需求；最终提示词不写具体工具调用次数
5. 在同一个提示词文件底部用 `---` 分隔一个备用提示词，标注“只有单独收到本段提示词后才实施”
6. 不设计多个后续任务块，不要求用户通过多次对话累积工具调用
7. 生成手动验证清单，按最终产物统一验收，目标 5-8 分钟走完

---

## 工具使用原则模板

首轮提示词必须完整包含以下 9 条；备用提示词可写“继续沿用首轮工具使用原则”：

```
## 工具使用原则

1. **强制分解任务**：把复杂任务拆成多个可执行子问题，通过逐个模块的探索、调研、实现、测试和验证完成；不要为了省事跳过验证，也不要用一次批量改写代替逐模块确认。
2. **工具优先**：能用工具获得的信息，不要猜。优先使用 `Read`、`Grep/Search`、`Glob`、`Bash/Terminal`、`Web Search`、`Browser`、`Edit`。
3. **方案调研**：涉及相关模块时，先用 `Web Search` 搜索社区方案或同类项目，对比优劣，再决定实现方式。
4. **逐步迭代**：保持"规划 → 调用工具 → 再规划 → 再调用工具 → 实现 → 验证"的循环，不要在信息不足时提前收敛。
5. **子 Agent 审查**：如果环境支持，方案、关键实现和测试失败修复后调用子 Agent 独立审查；由主 Agent 根据问题修复，再复查。
6. **sandbox 验证**：不确定的方案可先在 `sandbox/` 做小型 demo；确认可行后删除验证产物，再接入正式项目。
7. **自动化测试**：用 `Bash/Terminal` 运行构建、接口测试、自动化测试。测试不通过时定位修复再测。
8. **浏览器验证**：用 `Browser` 验证前台和后台用户可见功能。
9. **不破坏现有功能**：先从现有代码、文档和实际页面梳理项目的核心功能，实施过程中保持它们可用；新增功能、重构、迁移或安全加固后，必须回归验证受影响的既有主流程。
```

## 提示词结构模板

一个 Coding 任务提示词文件包含：

1. 首轮提示词标题
2. 任务背景（已有项目、技术栈、已有功能和必须保持的主流程）
3. 工具使用原则（完整写 9 条，要求按模块充分探索、实现和验证，但不规定具体工具调用次数）
4. 任务一~N（每项功能点逐条列出，并说明任务之间的先后依赖）
5. 自动化验证（逐条列出验证项）
6. 交付物（逐条列出）
7. `---` 分隔线
8. 备用提示词（标注“只有单独收到本段提示词后才实施”，继续沿用首轮工具使用原则）

## 功能类型经验参考

以下数据因项目而异，仅供估算轮次时参考，不是固定规则：

| 类型 | 经验调用次数 | 人工测试成本 | 说明 |
|------|-------------|------------|------|
| 功能开发（收藏、批量管理、审核流等） | 50-80/功能 | 极低（点几下验证） | 首选，跨文件读代码是自然行为 |
| 安全加固（SQL注入/XSS/CSRF审计） | 80-120 | 零（脚本验收） | 适合备用轮，逐接口 Read+Edit |
| 知识图谱/可视化 | 60-80 | 低（看一眼） | 需要 sandbox 验证 |
| 内容处理（摘要、标签、SEO） | 不稳定 | 零（脚本检测） | 需加反偷懒约束，轮次不可靠 |
| 既有功能与前序任务回归 | 20-40 | 零 | 首轮各任务完成后持续回归 |

实际选型按项目来，优先选"功能开发类"（因为模型实现一个中等功能，自然要跨文件读路由、组件、API、数据结构，工具调用自然就上去了）。

## 避坑经验

### 什么能逼出轮次

- **功能开发**：每个中等功能 50-80 次工具调用（理解现有代码→调研方案→写接口→写前端→调试→验证），这是最可靠的轮次来源
- **跨文件读代码**：模型理解一个功能需要读路由、读组件、读 API、读数据结构，这些是真实有效的工具调用
- **安全加固**：逐个接口 Read 检查 + Edit 修复，十几个接口 × 几次操作 = 80-120 次
- **跨任务回归**：首轮中每完成一个任务，都用 Browser 和自动化测试复查既有功能与前序任务，贡献 20-40 次

### 什么不能逼出轮次（实测验证）

- **逐篇读文章内容**（摘要重写、标签重建、SEO 元数据）：模型会用脚本批量生成，Read/Edit 走过场，实测轮次上不去
- **标签重建**：看 frontmatter 就能批量判断，不需要逐篇理解正文
- **内容巡检**：本身就是脚本扫描任务，工具调用集中在写脚本那几步
- **逐篇 Read/Edit 约束**：看似应该增加轮次，但模型会用各种方式规避（一次 Read 多篇、脚本批量扫描、跳过）

### 反偷懒措施（内容处理类任务必加）

- "禁止脚本批量读取、批量生成、批量写入"约束
- 机械验收标准（脚本检测覆盖率、重复率、字数、格式），卡住偷懒逼返工
- 每个任务阶段都安排前序功能回归，逼 Browser 实际验证

注意：即使加了这些约束，内容处理类任务的轮次贡献仍然不稳定。不要把轮次目标寄托在内容处理上，功能开发才是主力。

---

## 不增加测试工作量的关键

- **功能开发类**：选"点几下就能验证"的功能（收藏→看列表→取消，30秒测完）
- **安全加固类**：验收全靠脚本（注入测试+覆盖率扫描），零浏览器测试
- **内容处理类**：验收全靠脚本（重复率检测+格式检测），零浏览器测试
- **手动验证清单**：按最终产物统一验收，不按轮次拆分，目标 5-8 分钟走完
- **截图文件名=评价**：发现问题截图时文件名直接写问题描述，后续打分直接用

## Coding 任务评测输出

Coding 任务使用统一的 1–10 分评分，每个模型必须包含：

1、产物质量（0–10）：按平台官方标准定档，填写实际归因标签与评分依据；重点看功能、兼容性、关键约束和验收问题。评分依据至少 4 条。

2、执行过程（0–10）：按平台官方标准定档，填写实际归因标签与评分依据；重点看相对效率、用户介入、自测和验证行为。评分依据至少 4 条；不写具体耗时和工具调用数值，只写相对排名。

3、执行过程圈选评论：与产物质量、执行过程并列使用三级标题，仍须基于实际代码、真实行号和已读证据；每个模型至少 3 处，没有足够缺点时用亮点补足。

4、产出物反馈：逐条照搬本地验收截图文件名原话，不改写、不归纳，不保留图片扩展名。

5、归因标签：使用四级标题，汇总标签保持加粗；产物质量和执行过程的评分依据只写普通 `【标签】`，禁止使用颜色、HTML 或其他样式。

完整标题层级和字段顺序以 `references/测评结果示例.md` 的“统一测评结果模板”为准。
