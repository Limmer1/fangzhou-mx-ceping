## ⚠️ 第一原则：禁止瞎编

**所有输出内容必须基于实际读取的文件内容，不允许凭记忆、推测或印象编写。**

- 没读取过的代码或产物不写，不确定就先打开文件确认
- Coding 圈选使用真实代码和行号；Agent 圈选使用可复核的章节、页面、单元格、链接或产物位置
- 截图评论必须基于实际看到的截图文件名，不凭想象描述
- 不知道就说不知道，不编造
- 写之前先读，读完再写

## 配置

每次启动时先读取本 Skill 根目录下的 `config.json`，从其中获取“测评根目录”。公开的 `SKILL.md`、参考文件、示例配置和报告中不得写入用户真实本地路径。

`config.json` 不存在或字段不完整时，读取同目录下的 `config.example.json`，逐项向用户确认后再创建或补齐本地配置。真实 `config.json` 必须由 `.gitignore` 排除。

## 任务类型判断

先读取当期任务书，再按核心目标和主要交付物判断任务类型。只有两类：

| 判断条件 | 类型 | 典型工作 |
|----------|------|----------|
| 需要在已有代码仓库中探索、开发、重构、测试和回归 | Coding | 跨模块开发、修复、迁移、测试补齐 |
| 需要完成真实业务、办公、研究、数据处理、内容制作或辅助决策 | Agent | 调研、PPT、Excel、Word、HTML 报告、业务分析 |

使用 Python、SQL、浏览器、网页或脚本只是工作方式，不决定任务类型。两类任务统一使用“产物质量 + 执行过程 + 执行过程圈选评论 + 产出物反馈”的 1–10 分报告结构。

## 评价文字整理规则（所有类型共用）

撰写或修改评价前，读取并执行 `references/评价文字整理规则.md`；完成后按该规则复扫。Coding 与 Agent 保持原有适用要求。

## 目录结构规范

测评根目录从 `config.json` 读取。

```
{测评根目录}/
│
└── {YYYY-MM-DD}方舟{当期批次名}/          ← 每批次一个文件夹，名称以当期任务书为准
    ├── 任务书-{YYYY-MM-DD}.md               ← 本批次的官方任务书（从平台复制）
    ├── 方舟测评汇总-{YYYY-MM-DD}.md      ← 本批次最终汇总（所有项目）
    ├── {项目名}全部测评提交截图.jpg       ← 用户自己截图
    │
    ├── {项目名A}/                         ← 每个项目一个文件夹
    │   ├── {项目名A}-提示词.md            ← 发给模型的提示词
    │   ├── {项目名A}-自动化测试结果.md    ← AI 跑的自动化测试
    │   ├── {项目名A}-测评结果.md          ← 最终打分
    │   ├── 1、{模型1}/                    ← 序号来自平台截图，产物代码 + 问题截图
    │   ├── 2、{模型2}/
    │   └── 3、{模型3}/
    │
    ├── {项目名B}/
    │   └── ...（同上结构）
    │
    └── {项目名C}/
        └── ...（同上结构）
```

### 模型截图到达后的处理

1、按平台截图从上到下抄录模型，不按字母或分数排序。

2、给每个任务创建同序号的模型文件夹，格式固定为 `{序号}、{模型名}`。例如 `1、visor`、`2、wicket`、`3、xeric`、`4、yew`。

3、需要跟踪发送状态时，只在模型名后追加状态，例如 `1、visor【已发完】`，不能移动或重编号。

4、后续脚本识别模型名时，忽略开头的 `{数字}、` 和末尾的 `【状态】`；报告表格只显示模型名，不显示文件夹序号。

5、所有任务的数据统计、自动化测试、测评结果和批次汇总都按文件夹序号排列。资源管理器的显示顺序、模型得分和完成先后都不能覆盖该顺序。

## 主流程

### 步骤1：任务设计（准备阶段）

**触发**：用户说"准备测评"、"设计任务"，或新一批测评开始时

1. 从 Skill 根目录的 `config.json` 读取测评根目录。
2. 读取当期任务书，再读取 `types/Coding和Agent/评测标准.md` 和 `types/Coding和Agent/流程优化经验.md`。
3. 按“任务类型判断”确定 Coding 或 Agent，不根据使用了什么工具判断。
4. 与用户确认本批次日期、项目名称和交付物。模型列表优先从平台截图读取；截图未到时标记待补，不能猜顺序。
5. 输出拟创建的目录结构，等用户确认后再创建。
6. 根据任务类型读取对应指南并设计任务。最终发给模型的提示词不写工具调用次数，也不直接给结论或完整执行路径。
7. 用户在平台提交任务后，等待模型运行。平台截图到达后，按截图顺序创建编号模型文件夹。
8. 生成并行会话启动提示词，供后续项目分别测试。

#### Coding 任务

读取 `types/Coding和Agent/Coding/Coding任务设计指南.md`。Coding 沿用现有设计方法，必须基于已有代码仓库，不接受从零开发。

1. 先确认已有仓库、技术栈、现有功能和必须保持的主流程。
2. 单任务默认按不少于 400 次真实工具调用的工作量设计。当期任务书要求两个任务各 250 次或另有门槛时，以任务书为准。
3. 把多个相互关联的跨模块工作写进同一个首轮提示词，通过仓库探索、实现、测试和回归自然形成完整执行。
4. 文件底部只保留一个按需发送的备用提示词，不依赖后续多轮补齐核心需求。
5. 生成人工验证清单，按最终产物统一验收，目标 5–8 分钟完成。

#### Agent 任务

读取 `types/Coding和Agent/Agent/众测专家快速上手指南.md` 和 `types/Coding和Agent/Agent/Agent任务设计指南.md`。

1. 任务必须来自真实业务、办公、研究、内容制作、数据处理或辅助决策场景。
2. 当期任务书没有特殊规定时，按 3 个任务、每个任务每个模型不少于 100 次真实工具调用的工作量设计。
3. 写清真实背景、可用材料、业务约束、核心交付物和完成标准，保留模型自主判断方法和行动顺序的空间。
4. 交付物可为 HTML、PPT、Excel、Word、调研报告或其他办公产物。
5. 文件底部保留一个按需发送的备用提示词，用于扩大真实资料范围或补充核验。
6. 生成人工验证清单，只保留高价值检查项，目标 5–8 分钟完成。

**完成标记**：`echo "TASK_DESIGNED" >> scripts/.check_status`

**步骤完成时在对话中输出**：`[✓ 步骤1完成] 任务设计完成，已创建目录结构，任务说明已写入。等待平台模型运行。`

### 步骤2：下载产物

**触发**：平台模型运行完毕（约30分钟-1小时后）

下载由用户操作，AI 无法操作。

1. 提醒用户从平台下载各模型的产物压缩包或文件
2. 用户将 zip 放到对应的编号模型文件夹，例如 `1、visor`
3. 等待用户确认"下载好了"
4. 未就绪的模型标记"待补"，不阻塞流程

**完成标记**：`echo "DOWNLOAD_DONE" >> scripts/.check_status`

**步骤完成时在对话中输出**：`[✓ 步骤2完成] 用户确认产物已下载到位。`

### 步骤3：解压或确认已就绪

**触发**：用户确认下载完毕，或用户说"XX模型好了"

1. 如果用户提供了 zip 文件，AI 自动解压到对应模型文件夹（`unzip -o`）
2. 如果用户已自行解压，直接确认目录结构
3. 检查解压后的产物结构；Coding 识别前后端目录，Agent 识别主要交付文件和素材目录
4. 输出解压结果到对话供用户确认
5. **不需要等所有模型就绪**：已就绪的先处理，后续模型就绪后随时从步骤4补充
6. **生成并行会话启动提示词**：所有项目解压完成后，为每个项目生成独立会话的启动 prompt（见并行会话 Prompt 模板）。用户拿着 prompt 去开新会话，每个会话从步骤4开始独立执行。

**完成标记**：`echo "UNZIP_DONE" >> scripts/.check_status`

**步骤完成时在对话中输出**：`[✓ 步骤3完成] 解压完成，已生成并行会话提示词。`

### 步骤4：准备验证环境

对每个已就绪的模型，先判断任务类型和产物类型。任何测试都不得修改模型源代码、报告或其他交付物；需要生成日志、截图或临时数据时，放在测试目录或临时目录。

#### Coding

1. 查看 README、依赖清单和启动脚本，识别现有启动方式。
2. 按编号模型文件夹顺序分配端口，启动前检查占用。
3. 只补齐运行必需且用户已授权的环境配置，不改模型业务代码。
4. 启动服务并确认可访问，每启动一个模型立刻输出访问地址。
5. 用页面标题、入口文件或接口响应核对端口与模型，防止串号。
6. 启动失败时记录真实错误；未经用户授权，不修改模型产物来“修好”测试结果。

#### Agent

1. 盘点每个模型的交付文件、格式、文件大小和可打开性。
2. HTML 按需启动静态服务；PPT、Excel、Word、PDF 等使用对应工具只读检查。
3. 调研报告检查来源、链接、关键事实、日期和数据口径。
4. 不强制启动服务，也不为了统一流程把办公产物改造成网页。
5. 无法自动读取或渲染的内容明确标为人工验收项，不凭文件存在推断质量。

**完成标记**：`echo "ENV_READY" >> scripts/.check_status`

**步骤完成时在对话中输出**：`[✓ 步骤4完成] 验证环境已准备，模型产物未被修改。`

### 步骤5：手动测试引导 + 自动化测试（同步进行）

1. 读取当期任务书、项目提示词和交付要求。
2. 逐个模型检查交付物，记录真实通过项、失败项、限制和证据位置。
3. Coding 运行项目自带测试、构建、接口和浏览器回归，并检查真实代码位置。
4. Agent 按产物类型检查文件、来源、数据、页面、PPT 和办公产物；高风险事实做抽样交叉核验。
5. 输出 `{项目名}-自动化测试结果.md`，文件名尾缀按用户要求处理。
6. 自动化测试结束后，在当前会话输出 3–6 个最值得人工确认的问题，整体控制在 5–8 分钟。

问题驱动的手动验收重点必须写清：

1. 模型和产物。
2. 自动化发现。
3. 证据位置。
4. 为什么需要人工确认。
5. 具体怎么操作。
6. 什么现象算通过，什么现象算问题。

证据位置按任务类型处理：

1. Coding 使用真实文件路径、代码片段和行号。
2. Agent 使用执行轨迹、文件章节、页面位置、PPT 页码、表格单元格、来源链接或其他可复核位置。

规则：

1. 区分“已确认的问题”和“需要人工确认的风险”，不能把风险写成结论。
2. 已经自动化确认通过的项目不重复让用户验收。
3. 自动化没有发现明确问题时直接说明，只列与任务有关的自动化盲区。
4. 用户截图与自动化结果冲突时，以用户实际验收和截图为准。
5. 用户发现的问题截图放入对应编号模型文件夹，文件名就是反馈评价。

**完成标记**：`echo "TEST_DONE" >> scripts/.check_status`

**步骤完成时在对话中输出**：`[✓ 步骤5完成] 自动化测试完成，已按真实问题输出手动验收重点，等待用户截图。`
### 步骤6：评分

**触发**：用户确认手动测试完成、截图已放好

**评分前必须先执行“评价文字整理规则（所有类型共用）”。**

1. **读取用户截图**：必须识别图片内容 + 读取文件名（文件名=问题描述/反馈评价）
2. **读取平台执行数据截图**：用户会在模型文件夹放一张平台截图，包含耗时、用户轮次、工具轮次等数据
3. 综合截图 + 自动化测试，逐模型评分

#### 统一评分

Coding 与 Agent 都使用 `types/Coding和Agent/评测标准.md` 的平台 1–10 分标准。

1. 产物质量 0–10 分。根据核心要求、准确性、完整性、可用性、关键约束和人工验收问题定档。
2. 执行过程 0–10 分。根据相对效率、用户介入、自测、验证和异常处理定档；具体耗时与调用次数放在数据统计文档。
3. 两项评分都要填写真实归因标签和至少 4 条依据。标签名称与解释必须逐字使用评测标准原文。
4. 执行过程圈选评论每个模型至少 3 处。Coding 使用真实代码和行号；Agent 使用可复核的执行轨迹、章节、页面、页码、单元格、链接或产物位置。
5. 产出物反馈逐条使用截图文件名原话，不改写、不归纳，不保留图片后缀。
6. 产物质量、执行过程和圈选评论使用用户本人准备提交平台的口吻，遵守文字整理规则。
7. 评分表和逐模型章节按编号文件夹顺序排列；单独的综合排名写真实名次。
8. 自动化测试、用户截图和平台执行数据要相互对照。发生冲突时，以用户实际操作和截图为准，并说明证据限制。

评分后必须逐项确认：

1. 两项分数与平台 1–10 分标准一致。
2. 每项评分依据不少于 4 条，标签都有证据。
3. 每个模型至少 3 处圈选评论，证据位置已核对。
4. 产出物反馈保持截图文件名原话。
5. 评价已调用文字整理 Skill 复扫，口吻、字数、禁用句式和模型顺序均通过。
6. 产物质量最高分与最低分相差不少于 2 分；分差必须由实际证据支撑。
**完成标记**：`echo "SCORING_DONE" >> scripts/.check_status`

**步骤完成时在对话中输出**：`[✓ 步骤6完成] 评分完成，平台分档✓、分差>=2✓、各维度理由✓、圈选证据✓。`

### 步骤7：生成测评报告

写入路径：`{测评根目录}/{批次文件夹}/{项目名}/{项目名}-测评结果.md`

注意：文件名必须是当前项目名，不要搞混。如当前是项目A，就写入 `{项目名A}-测评结果.md`。

**格式规则**：

1. 统一使用“评分汇总 → 各模型产物质量 → 执行过程 → 执行过程圈选评论 → 产出物反馈”的结构。
2. 模型行与逐模型章节按编号文件夹顺序排列，不按字母、分数或效率重排。
3. 排名字段和综合排名写真实名次。
4. 所有评价执行“评价文字整理规则”，每点以 40–50 字为目标。
5. 归因标签使用四级标题，评分依据使用普通 `【标签】`。
6. 产出物反馈只写截图文件名原话，不保留图片后缀。
7. Coding 圈选写真实文件、行号和代码片段；Agent 圈选写可复核的轨迹、章节、页面、页码、单元格、链接或产物位置。

详细格式参考 `types/Coding和Agent/测评结果示例.md`。

## 多会话协作

每个项目对应一个独立会话，不在同一个会话中测评多个项目。

## 沟通规范

- 简洁直接，不写代码审查报告
- 评价写法统一执行“评价文字整理规则（所有类型共用）”
- **截图说了算**，不质疑用户观察。用户截图文件名里写的就是反馈评价
- **必须读取用户截图内容**，识别图片中的UI状态
- 分数敢拉开差距，不和稀泥
- 圈选评论按任务类型定位。Coding 使用文件名、行号和代码片段；Agent 使用可复核的章节、页面、页码、单元格、链接或产物位置
- 路径不确定时主动问用户确认
- **列表格式**：所有输出内容不用 Markdown 无序列表 `- ` 和有序列表 `1.`，统一用中文顿号序号 `1、` `2、` `3、`（Markdown 列表复制到评测平台渲染异常）
- **禁止瞎编**：所有描述必须基于实际读取的文件内容。没看过的代码不写，不确定的先 Read 确认再写。不知道就说不知道，不要凭印象编造

## 打分注意事项

- 打分必须有区分度，不能所有模型分数趋同（最高-最低 >= 2）
- 每个维度都要写理由
- 评价写法统一执行“评价文字整理规则（所有类型共用）”
- 执行过程重点看模型是否充分验证，以及是否提前宣称完成
- 评分完成后必须在对话中输出逐条检查确认结果
- **圈选证据必须真实可复核**：Coding 的代码和行号必须从实际文件核对；Agent 的章节、页面、页码、单元格、链接或产物位置必须真实存在。写之前先读，读完再写
