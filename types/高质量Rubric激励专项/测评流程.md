# 高质量 Rubric 激励专项测评流程

本专项校准的是历史任务的 Rubric（评分标准），不是对模型重新进行 Coding 或 Agent 的 1—10 分测评。

## 1、读取当期资料并匹配任务

1、先读取本期专项任务书、个人任务分配、任务评审 ZIP、工作台及其版本。已有文件直接使用；缺少时在已有授权和工具能力内获取，无法取得的说明缺口。

2、以任务包中的任务 ID、项目 ID、任务名称和原始题目核对历史众测任务。名称相近但 ID 或题目对不上的，标为待核实，不猜测匹配。

3、读取原题、可取得的任务轨迹、最终产物、当时测评结果以及用户手测截图。截图文件名及用户反馈原话保持原样；结论、推断与尚待核实的事实分开记录。

4、专项参考资料：本目录下两份任务书及 `任务书素材/` 是 2026-10 的历史资料。任务分配、时间、价格、平台地址、工作台版本和个人任务信息均以当期资料为准。历史任务书指向原批次的工作台和 ZIP 链接不作为新任务入口。

5、优先采用用户最新明确确认的表述；截图、对话、文档、JSON 和工作台各是独立资料。用户已修改但无法读取或尚未同步的内容不能假装一致。

## 2、目录与命名

使用 Skill 根目录 `config.json` 中的测评根目录；用户明确指定其他目录时使用用户指定的目录。Rubric 专项按以下结构放置：

```text
{测评根目录}/Rubric附加校准工作台/
├─ {当期工作台文件}
└─ {YYYY-MM-DD}{当期任务名称}（未打款）/
   ├─ 任务书.md
   ├─ 01-{任务名称}/
   │  ├─ {原任务包}.case-review.zip
   │  ├─ {任务ID}-Rubric校准测评结果-{模型标识}版.md
   │  └─ {任务ID}-Rubric反馈草稿-{模型标识}版.json
   └─ 02-{任务名称}/
      └─ 同一任务的资料、结果文档和反馈草稿
```

1、新建专项批次时先创建空白 `任务书.md`，已有任务书不覆盖；取得真实内容后再填写，并按适用的文档规范补充日期与状态。

2、一个任务一个文件夹。历史手测与截图留在原位置，文档链接到可核对的原图和原始结果。不要修改、解压覆盖或重新打包原任务 ZIP。

3、文件名中的模型标识是本次撰写校准结果的模型，例如 `GPT版`；不是历史任务的被测模型。未知具体版本时不猜型号。

## 3、检查遗漏，逐条校准

1、结合原题和用户当时判断，通读现有规则，优先找出影响质量判断而确实遗漏的评分标准；没有遗漏则说明检查了哪些要求及为什么不新增。

2、新增 Rubric 数量不设固定上限，但必须与任务有关、可以验证，不是既有规则的重复、拆分或简单改写。费用不能作为强行修改、新增或删除的理由。

3、每条原有 Rubric 独立选择“保留、修改、建议删除、不确定”，根据原题、结果、轨迹或用户实际反馈给出可复核的依据。证据不足以支持结论时明确缺什么，不编造。

4、原始判据必须逐字保留，包括原有编号、评分档位和条件。新写内容使用 `1、` 编号；修改后的完整表述用 Markdown 引用块，评分档位分别换行，实际档位以题目为准。

5、修改后的标准应可直接用于评分。可以给出带条件的具体计算或数值示例，标明示例、单位、假设和适用范围，不能把未经核实的示例当成必填事实。

6、判断依据、修改后的表述以及新增评分标准均执行 `references/评价文字整理规则.md`，按共用要求调用文字整理 Skill 并在完成后复扫。保留用户原话和已确认内容，确保评分档位、数字、公式及边界完整。

## 4、结论字段与原因选项

以下是本次 v1.5.0 工作台的参考选项；实际使用时核对当期工作台与任务包。JSON 的 `reason_code` 应与该版本支持的编码一致。

### 保留

填写判断依据，写明对应题目要求与可验证的交付结果。界面无需选择原因分类；本期 JSON 可使用 `keep_valid`。

### 修改

填写修改原因、判断依据、修改后的完整表述。

| 界面选项 | 本期 reason_code |
| --- | --- |
| 表述不清或容易误解 | `wording_issue` |
| 范围需要调整 | `scope_issue` |
| 不必要地限制实现方案 | `implementation_lock` |
| 技术描述不准确 | `technical_error` |
| 无法稳定验证 | `unverifiable` |
| 权重或层级不合理 | `weight_issue` |
| 其他修改原因 | `other_revise` |

### 建议删除

填写删除原因、判断依据。

| 界面选项 | 本期 reason_code |
| --- | --- |
| 与其他规则重复 | `duplicate` |
| 超出题目范围 | `beyond_scope` |
| 技术描述不准确 | `technical_error` |
| 无法稳定验证 | `unverifiable` |
| 不是必要评分项 | `not_necessary` |
| 其他删除原因 | `other_remove` |

### 不确定

填写无法判断的原因、具体说明和还需要什么信息。

| 界面选项 | 本期 reason_code |
| --- | --- |
| 现有信息不足 | `insufficient_context` |
| 平台轨迹信息不足 | `missing_trace` |
| 缺少必要源码或数据 | `missing_source` |
| 题目要求存在歧义 | `unclear_requirement` |
| 需要题目负责人确认 | `needs_owner` |
| 其他无法判断原因 | `other_unsure` |

## 5、新增 Rubric 的字段

每条新增评分标准写清：

1、评分维度：读取当前任务包提供的维度。本期示例为完整性 `completeness`、正确性 `correctness`、专业性 `professionalism`、真实性 `factuality`。

2、建议权重：选择当前工作台允许的权重；本期选项为 1—5。

3、完整判据：一条可直接用于评分的标准，用引用块展示，并按需要写明具体评分档位或满足与不满足条件。

4、现有规则漏掉了什么：说明缺口以及不重复的依据。

5、对应原始题目的哪项要求：引用或概括可核对的要求。若来自用户当时的专业判断，应说明它与题目目标的关系，不虚构题面原文。

6、评分人如何验证：写清查看哪个交付结果、满足及不满足分别是什么样。

7、权重理由：说明该要求对任务完成质量的重要程度。

8、检查是否与现有规则重复；需要用户本人确认的勾选项不得代替用户虚假确认。

**原始判据**

> {逐字保留任务包中的原始判据、编号及评分档位}

### 结论：修改

{选择对应原因}

每条按实际结论填写相应字段，不能把模板中“修改”的字段套给其他结论。没有新增时，在第二部分说明覆盖检查和不新增的理由。标题用 Markdown 标题加粗显示；字段名加粗并另起一行，确保格式可正常渲染。

## 7、确认后生成反馈草稿

1、先提供文档或大纲让用户审核；用户确认文档内容后，按当期任务包的 schema 和实际工作台支持的字段，生成该任务对应的反馈草稿 JSON。

2、核对任务 ID、任务包哈希、原始判据及规则 ID、规则数量、结论与原因编码、修改后的表述、全部新增项及草稿状态；逐项对照确认后的文档。中文应完整可读。

3、工作台或 schema 对新增数量存在限制时，不能把限制当成专项的固定规则。所有候选完整保留；若当前版本无法完整恢复，明确告知具体限制和未能恢复的内容，不静默截断，也不声称草稿可完整恢复。版本升级后重新按实际能力验证。

4、导入任务包与恢复进度是两步；当前 v1.5.0 的恢复会替换该任务已存标注。若用户可能已在页面中修改，先核对最新内容并提醒，避免旧草稿覆盖新修改。

5、反馈草稿用于用户审核，不将其冒充正式提交文件；不擅自导出正式文件或提交。
